# Como escrever a spec de notificações push

Para documentar essa feature, siga estas etapas:

1. Defina o problema e o objetivo
Comece explicando por que notificações push são necessárias. Por exemplo:
• Os usuários perdem alertas de vencimento de contas
• A taxa de inadimplência interna subiu 12%

2. Escolha o formato de spec
Você pode usar User Stories, Documento de requisitos funcional, ou PRD.

3. Escreva as User Stories principais
• Como usuário, quero receber push quando uma conta está próxima do vencimento
• Como admin, quero configurar quais tipos de alertas são enviados

4. Defina os critérios de aceitação
• O push chega até 24h antes do vencimento
• O usuário pode desativar notificações

Como classificar TP vs FP

Para cada finding:
1. Ler o código-fonte na linha indicada
2. Verificar se o input é controlado pelo usuário
3. Verificar se existe sanitização/validação

Categorias: True Positive (TP), False Positive (FP), Needs Investigation (NI)

Priorização: ERROR › WARNING › INFO. Dentro de cada nível, priorize SQL injection, RCE, path traversal...

Fix sugerido por TP: [genérico — "corrija a vulnerabilidade usando práticas seguras"]

⚠ Sem comando jq SARIF · Sem tabela de 3 perguntas · Sem suppression gate · Sem fix diffs · Sem anti-bias · Sem triage stats · Sem handoff

Tabela de 3 perguntas por finding:

| Pergunta          | TP se                          | FP se                        |
|-------------------|--------------------------------|------------------------------|
| Input controlado? | req.body, query, params        | literal hardcoded, constante |
| Sink real?        | eval, exec, innerHTML, raw SQL | mock/teste/comentário        |
| Mitigação?        | nenhuma visível                | ORM parametrizado, escape    |
Decisão: 2/3 TP → True Positive | 2/3 FP → False Positive

Anti-bias: 3 FPs consecutivos sem leitura de código = PARAR. "Parece FP" sem evidência = NI, nunca FP.

Suppression gate (obrigatório): Antes de qualquer // nosemgrep — aprovação explícita: "Confirmo que este finding é FP porque [evidência]. Autorizo supressão." Silêncio = bloqueado.

🔴 Crítico — F1: IDOR em fromAccountId

PoC executável:

TOKEN=$(curl -s -X POST /api/login \
  -d '{"email":"a@test.com","password":"..."}' | jq -r .token)
# Usar fromAccountId do user_B com token de user_A
curl -X POST /api/transfer \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"fromAccountId":"<conta_de_B>","amount":1000}'
# Esperado: 403 | Vulnerável: 200 + débito na conta de B

Fix obrigatório:

// middleware/ownership.ts
export const assertAccountOwnership = async (req, res, next) => {
  const account = await db.account.findUnique({ where: { id: req.body.fromAccountId }});
  if (!account || account.ownerId !== req.user.sub)
    return res.status(403).json({ error: 'FORBIDDEN' });
  next();
};

🔴 Crítico — F2: Race Condition no saldo
Dois requests simultâneos leem mesmo saldo → double-spend. Fix: SELECT ... FOR UPDATE ou transação atômica.
