1. **Raw recall**: load `decisions.md` (167 lines) + last N session logs → verbose, expensive, noisy

### Bugs found and fixed during bench

Two bugs in `l3-persona-generator.mjs` were discovered and fixed as part of this bench:

1. **Windows CRLF issue** — `decisions.md` uses `\r\n` line endings. `split("\n\n")` on CRLF content produces empty paragraphs. Fix: normalize to `\n` before parsing (applied to both `parseFrontmatter` and `parseDecisions`).

2. **Scenario summary extraction** — parser was using `slice(1,2)` on `\n\n`-split blocks, which hit empty strings before the first real paragraph. Fix: filter empty paragraphs + strip bold label prefixes (`**Decisão:**` etc) to extract meaningful content.

### Caveats

- **0 L1 atoms** in this vault — the `D:/claude-memory` vault uses chronological logs, not `memory/*.md` atom files. The persona runs on L2 scenarios only (decisions.md). To get L1 atoms contributing, run `/consolidate-memory` and extract atoms from session logs into `memory/feedback_*.md` etc.
- **94% is upper-bound** for this run — if the agent had loaded decisions.md + 10 logs instead of 5, savings would be even higher. If only decisions.md (no logs), savings drop to ~74%.
- **Token estimate is bytes÷4** — same approximation as `bench/run.mjs`.

## Part 2 — Swarm Diagnostics

### 2a. agent-dispatch-validator: "nunca disparou" — is this a bug?

**Finding: it's working correctly, just not triggered by the recent run.**

From `.bot/agent-dispatch-errors.jsonl`:

| Date | Blocks |
|---|---|

| After 2026-05-20 | **0** |
| **Last entry** | 2026-05-20T21:42:00Z |

All 12 historical blocks were **test runs** (testing the validator itself, during v2.2.0 development):

| Blocked type | Count |
|---|---|
| `dev-team-kit-fv:04-frontend-integration` (skill passed as agent) | 6 |
| `dev-team-kit-fv:nonexistent-name` (unknown name) | 5 |
| `dev-team-kit-fv:nonexistent-agent` (unknown name) | 1 |

**The swarm session of auth social (2026-05-19) had 4 review agents fail with "credits exhausted"** — not with invalid dispatch. The validator correctly did NOT fire because:

- The 4 review subagents (`code-reviewer`, `security-auditor`, `test-engineer`, `anti-ai-writing`) ARE valid subagent names in `agents/`
- The dispatch was valid — agents failed at runtime (credits), not at pre-tool-use validation
- Validator = "blocks wrong names". It cannot detect "provider out of credits" — that's a different failure mode

**Conclusion:** validator is working. The credits failure is a separate concern — currently unhandled silently. 

**Recommendation**: add a check in `/savings` or `/swarm` synthesis step that detects when agents returned empty/error output and surface it explicitly (not confuse with "validator never fired = silent bug").

### 2b. Write×130 hot file — what it means and what to do

**Context**: the `/savings` skill reports a `Write × 130` hot-file score when a single `/swarm` session scaffolds an entire new project. 130 writes = ~full Turborepo + auth + DB structure.

**Is this a problem?** Not a bug — it's expected for greenfield scaffolding. But it's a signal:

- 130 writes means the agent wrote every file from scratch
- No template, no skip-phase, no "already done" detection
- The first 3 phases (spec → schema → folder structure) are identical for any Turborepo + Better Auth + Drizzle + Shadcn project

**What the swarm correctly suggested**: create a **learned-skill or template** that encodes the repeatable scaffold so future `/swarm` starts from phase 4 instead of phase 1.

**Action**: create `templates/turborepo-better-auth-drizzle-shadcn/` with:
- `package.json` base
- `turbo.json` + workspace layout
- `drizzle.config.ts`
- `auth.config.ts` (Better Auth)
- `apps/web/` structure stub

This turns 130 writes into ~20 writes (the novel feature code) on the next identical project.

**Priority**: medium — only relevant if you scaffold that same stack again. Track in `learned-skills/turborepo-scaffold.md` with score 0.5 until the next time it's needed.
